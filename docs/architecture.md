# Architecture

Kotlin Syntax centers on a portable Kotlin Multiplatform parser. The VS Code extension and online playground are consumers of the same library.

## Modules

- `kotlin-parser/src/commonMain`: lexer, marker builder, immutable syntax trees, grammar parsing and incremental documents.
- `kotlin-parser/src/jvmTest`: official compiler adapters and differential tests. The compiler dependency is limited to this source set.
- `kotlin-parser/src/wasmJsMain`: exported document, parsing and syntax classification APIs.
- `kotlin-format/src/commonMain`: ktfmt rules, portable tree views, KDoc formatting and the google-java-format layout engine. `jvmTest` alone depends on the original formatters; JVM and WASM production code use the portable parser.
- `kotlin-parser/js`: shared token legend and source replacement calculation, exported from the lightweight `kotlin-parser/editor` entry and copied into the extension package with the parser assets.
- `kotlin-vscode/src`: extension provider, Worker client, Worker runtime and token encoding.
- `kotlin-website/src`: React playground and browser Worker. Theme preparation resolves the vendored One Dark Pro rules into deduplicated styles before Vite builds the site.
- `benchmarks`: executable benchmarks and archived reports; see the [benchmark guide](../benchmarks/README.md).

## Kotlin API

The formatter API and pinned upstream versions are described in [Kotlin formatting](formatting.md). The extension loads its separate WASM formatter Worker on the first formatting request. Formatting uses a complete source snapshot; cancelled or outdated results are discarded before producing editor edits.

`tokenize` returns `List<Token>`; `parseFile` and `parseScript` return `SyntaxNode`. `SyntaxNode.classifySyntax()` returns `List<SyntaxClassification>` with `TokenType` and `Set<TokenModifier>`. `IncrementalDocument` keeps native Kotlin document state. Android and JVM consumers use these objects directly; JSON is only needed at serialization boundaries. See [Kotlin and Android integration](kotlin-api.md).

## JavaScript entry

`kotlin-parser/editor` exports `tokenTypes`, `tokenModifiers` and `replacement`, built with tsdown. Importing this entry does not load WASM. There is no root package entry; consumers explicitly select editor utilities or the WASM API. The `kotlin-parser/wasm` subpath exposes the generated Kotlin module; use a static import or `await import('kotlin-parser/wasm')` for on-demand loading. Parsing/document methods remain synchronous after module initialization. Repeated imports reuse the module in the same JS environment; each Worker has its own instance. The website Worker imports `kotlin-parser/wasm` directly. Vite tracks the generated modules and emits the referenced WASM asset with the Worker build.

## WASM API

The common Kotlin parser foundation now includes immutable syntax nodes, a marker builder (`mark`, `done`, `drop`, `precede`, `rollbackTo`, `collapse`, `doneBefore`, and error nodes), comment binding, newline state, and joined operator tokens. JVM tests compare marker trees and semantic adapter behavior with the pinned official compiler; common tests also run on WASM. This is the subset needed for the non-lazy parser, not a complete IntelliJ builder implementation.

The parser package exports `tokenize(source): string`, returning JSON tokens `{ kind, start, end }`. Offsets are UTF-16 code units; whitespace is retained. Incomplete strings can yield the official lexer's zero-length `DANGLING_NEWLINE` token. Token names are upstream constant names, not resolved symbols.

`parseFile(source): string` returns a JSON syntax tree with `{ kind, start, end, children, error }` on every node. It preserves whitespace/comments and zero-width error nodes. `error` is a message or `null`; the root kind is `KT_FILE`. Input is passed directly to the lexer without line-ending normalization.

`parseScript(source): string` uses the same JSON format and includes a `SCRIPT` node containing top-level statements. Both entry points parse syntax only; they do not resolve symbols or check Kotlin type correctness.

The WASM API exports `openDocument(source, script): number`, `documentTree(id): string`, `editDocument(id, start, end, replacement): string` and `closeDocument(id)`. Edit offsets address the current document in UTF-16 code units; `end` is exclusive. Close document handles when finished. Multiple edits expressed against one source snapshot must be applied from the highest offset downwards.

## Incremental documents

The incremental implementation retains immutable prefix nodes and reparses from the preceding top-level declaration to EOF. It requires at least two declarations strictly before the edit and an error-free prior tree. Preamble edits, scripts and previously damaged trees use full parsing. This is conservative incremental parsing, not arbitrary subtree reparsing or incremental lexing; edits near the beginning or inside a large first declaration can still reparse the entire file. The common JVM/WASM suite compares insertion, deletion, replacement and sequential-edit results with fresh parsing, and verifies prefix-node reuse.

## Highlighting data flow

Editor changes (snapshot for initialization/recovery) → ParserClient queue → Node Worker → WASM document update → compact syntax classifications → per-line token encoding → transferable Uint32Array → VS Code semantic tokens.

The extension classifies syntax through VS Code's semantic token API. Multiline spans are split into valid per-line tokens. Document versions, edits at multiple offsets, cancellation checks, delta result IDs and closing documents are handled. The extension host sends versioned edit batches to a single Worker. It keeps one running request plus the newest queued result request per document and operation, while retaining the intervening edits even when requests are superseded or cancelled. Batch ranges use pre-edit UTF-16 offsets and are sorted in descending order; batches are applied chronologically. The Worker combines them into one enclosing replacement before parsing and returns the target version with the encoded tokens. Initial documents, mode changes, missed change notifications and Worker restarts use full snapshots. A mismatched base version requests snapshot resynchronization without applying the edits. More than 64 unsent batches discard the edit history in favor of the latest snapshot. The host still captures document text for recovery, but normal edit messages do not carry it. Closing a document drops its cache, and disposal terminates the Worker. Cancellation discards results and queued work; it cannot interrupt a synchronous WASM parse that is already running. Classification is syntactic: an unresolved reference cannot reliably be identified as a class, function or property solely from its spelling.

`applyDocumentEdit(id, start, end, replacement): void` updates a document without serializing its tree. `documentClassifications(id): Int32Array` returns a new native JS typed array repeating `[start, end, tokenTypeIndex, modifierBits]`; token IDs follow the Kotlin `TokenType` order. `tokenLegend()` exports the type and modifier names; the JS build generates its legend from that export. The existing JSON tree APIs remain available for tooling/tests. The WASM export fills the typed array directly, without JSON serialization or parsing. The website Worker transfers its buffer to the main thread. The extension splits multiline spans and transfers encoded `Uint32Array` tokens, retaining its existing cache. Transferring the returned classification buffer detaches that JS array without affecting the Kotlin document; later calls return independent buffers. The generated TypeScript return declaration is corrected during the build because Kotlin/Wasm exports `JsAny` as `NonNullable<unknown>`.

The website composes pending CodeMirror ChangeSets while its Worker is busy, then sends descending edit ranges with base/target versions. It materializes the full source only for initialization, mode changes or recovery. Its Worker also parses one enclosing replacement per request and transfers the classification buffer. Both consumers retain the current editor document as the source of truth; external disk changes enter through editor document-change events.

The legacy classifier in `kotlin-vscode/test/legacy-highlights.ts` remains a reference for differential testing and benchmarks. `protocol.ts` encodes compact spans; `parser-worker.ts` owns the WASM document handles.

Classification is collected internally into a growable `IntArray` of four integers per span. The WASM export copies those integers into its returned JS typed array without creating `SyntaxClassification` objects or modifier sets. The public Kotlin `classifySyntax()` API materializes its existing objects from the same integer results; modifier sets are created only for nonzero masks. This keeps one classification implementation and the same result fields and wire format.

## Definition navigation

`DefinitionIndex` in common Kotlin builds lexical scopes from the existing tree and source. `IncrementalDocument.definitionsAt(offset)` builds it lazily and reuses it until the next edit, which invalidates the whole index. It returns `DefinitionTarget` ranges for declarations or explicit imports; it does not perform type inference or overload selection. The WASM `documentDefinitions(id, offset)` export returns an `Int32Array` repeating `[declarationStart, declarationEnd, nameStart, nameEnd]`, with UTF-16 offsets and exclusive ends. Empty results mean unresolved. No syntax-tree JSON transfer is needed.

The VS Code definition provider sends a versioned query through the existing document synchronization path. The client keeps the newest queued request per document and operation, so highlighting and navigation do not supersede each other. Edits and closure invalidate both operations. The Worker shares the same WASM document for both and returns only definition ranges for navigation queries. The provider checks the document version before converting ranges to same-document definition links. Document highlighting reuses the same-file lexical index, overlays known declaration categories and explicit type/object member paths, and caches the compact result until an edit. It never invokes workspace lookup. The raw tree classifySyntax API remains syntax-only.

A separate lazy `LocalNavigation` index retains same-file declaration identities, including local classes and functions, and is invalidated on edits. It resolves local qualified members, class/instance callable references, named parameters (including overload candidates) and type-alias constructor parameters without workspace access. Navigation queries preserve bound type identities and nested type paths instead of repeating lookup by spelling. When an unknown lambda receiver has a syntactically known local type, its matching members and enclosing member candidates are returned together; this does not claim compiler overload or lambda-receiver resolution. Local captures retain priority. Member privacy is checked against enclosing declaration ranges, including in workspace summaries. Highlighting continues to use the strict lexical index and does not consume navigation candidates.

File symbol summaries also carry expect/actual roles, modifier ranges and syntactic receiver/parameter signatures. Expected members inherit their role from the containing expected type; ordinary members of actual types do not automatically become actual declarations. Annotation primary constructors inherit the actual role even when their modifier is omitted. The extension handles modifier/declaration-name navigation and Go to Implementation on expected declarations through the same Worker and workspace summary cache. Counterpart lookup searches other standard Main or Test source sets in the same module, independently of file names or package directory layout, and returns all matching candidates with an origin selection range. Signatures normalize generic parameter names, explicit import aliases and known lexical type paths. Enclosing member types precede explicit imports, which precede file-level types. Signatures use on-demand type declaration lookup in the module's matching Main or Test source sets, including the current source set. `NameResolver` in `type-resolution.ts` shares the binding order with ordinary receiver navigation: enclosing member scopes, explicit imports, file/package declarations, star imports, known default-import classifiers, then written qualified names. Each tier binds independently; identities from lower tiers are not mixed into higher-priority results. Type identities carry their qualified path and evidence source, and resolutions distinguish resolved, ambiguous and unresolved results. Signature matching requires resolved identities; unavailable star-import dependency types remain unresolved. The finite standard-library classifier catalog supplies default-import identities without inventing package prefixes for arbitrary names. Receiver types retain the declaring file and owner path, so moving a declaration to another file preserves its nested-type context. This does not introduce compiler type inference. Highlighting never requests these workspace searches. Source-set dependency graphs, custom source roots and underlying members of actual type aliases remain outside this lookup.

## Build and native TypeScript

VS Code extends explicit-import destinations and eligible unresolved same-package references with on-demand workspace lookup. `documentExternalReference(id, offset)` uses the lexical index to distinguish eligible unqualified references from locals, qualified selectors, comments and unknown receivers. Same-package lookup also checks the current directory, validates the actual package, filters type references to type declarations and excludes receiver-dependent extension declarations. `documentSymbols(id)` returns compact JSON containing package components, import paths and declaration ranges with owner paths, visibility, companion aliases and syntactic type hints from the existing tree. `WorkspaceDefinitions` adapts requests and editor locations; `WorkspaceSymbols` owns file retrieval, snapshots and caches, without deciding name-binding priority. It enumerates workspace `.kt` paths while pruning directories using each workspace root and nested `.gitignore` files, selects matching full package directories or known roots with omitted package prefixes, reads candidate contents and applies an indexOf-based Kotlin identifier-boundary filter before requesting their summaries. It prefers unsaved open documents, verifies actual package and declaration names, and preserves all candidates without resolving Gradle/module visibility. Unresolved imports retain their original destination. The bounded summary cache is keyed by URI and content hash; the first lookup discovers package directories, then later lookups enumerate only selected package directories and their ancestors to apply ignore rules. File creation/deletion, ignore-file changes and workspace changes invalidate the directory inventory. An unsuccessful directed lookup can refresh the inventory once per request. For explicit object-member imports, possible package/owner splits are searched and the entire parsed package plus declaration path must match; private owners and ordinary class instance members are excluded. Temporary candidate document handles are closed after extraction. The shared Worker queue prefers highlighting and lexical navigation over summary work between requests; it cannot interrupt a running parse. No startup content scan or complete project symbol index is built. Import summaries retain identifier segment ranges so clicking an object or member within an import searches that exact path prefix. Names with explicit imports can expose import-only queries across unknown receiver scopes without claiming semantic resolution. When an unqualified call without an explicit import crosses an unknown receiver scope, the lexical index can expose a constructor-only query; workspace lookup then accepts only class/typealias declarations and honors explicit import aliases. Captured lexical callables retain priority. This is candidate navigation, not constructor overload or receiver resolution. Website navigation remains single-file.

Handwritten source, development scripts and tests use TypeScript with explicit `.ts` source imports. Node runs development scripts directly. The extension release build uses tsdown to bundle ESM JavaScript with fixed `dist/extension.js` and `dist/parser-worker.js` entries. Auxiliary `parser-client`, `protocol` and `highlights` entries preserve the built-code imports used by tests and benchmarks. Shared parser utilities are bundled; `vscode`, Node built-ins and the Kotlin WASM module remain external. Kotlin-generated `.mjs` glue, WASM and their declarations are copied into `dist/parser/`. Declaration files support local test/benchmark typechecking but are excluded from VSIX packaging.

`tsconfig.base.json` supplies shared strict checking and native-TypeScript constraints. `pnpm typecheck` uses TypeScript without emitting; tsdown generates JavaScript and uses Oxc for declaration output. The package remains `type: module`. The editor version requirement remains unchanged; this packaging change does not establish compatibility with older editor releases.

`pnpm-lock.yaml` locks the workspace packages. `kotlin-js-store/wasm/package-lock.json` is the separate Kotlin Gradle plugin test-harness lockfile; it does not manage the workspace packages.

Detailed validation commands are in [testing.md](testing.md); grammar boundaries are in [compatibility.md](compatibility.md).

Syntax-only classification distinguishes enum and annotation declarations, member methods, labels, constructor properties and local variables. Declaration modifiers include `readonly` for `val`, explicit `abstract`, and `async` for `suspend`; KDoc spans carry `documentation`. These modifiers do not imply symbol resolution: reference mutability, deprecation and standard-library membership are not inferred. Script-root declarations are properties even though the parser wraps them in a block.

Qualified navigation uses `documentNavigationQuery(id, offset)` and a separate TypeScript query planner. The query records lexical receiver bindings, explicit types or simple constructor initializers. Declaration summaries include nested types, objects, companion aliases, enum entries and instance members. Package wildcard imports are searched after same-package candidates. Candidate file text and parsed summaries are reused within one request; the persistent summary cache remains bounded across requests. This prevents repeated parsing within a large lookup when it exceeds the persistent cache capacity. No general type inference, inheritance traversal, overload selection or module graph is introduced.

Editor documents adapt CR line endings to LF at the same UTF-16 positions before parsing, including incremental suffix parses. Original document text and all offsets remain unchanged. This prevents CRLF from breaking import lists and declarations while leaving the raw lexer/parser APIs and official differential inputs unchanged.

Type-use evidence is collected only from explicit, unqualified type references in the current file. It is associated with an explicit import identity or lexical scope and reused for compatible value references after checking local bindings. Qualified package prefixes, uppercase calls and class literals do not establish type evidence. Supertype constructor callees use type coloring; annotation callees retain decorator coloring. No external file is read for these classifications.

Single-file expression highlighting indexes local members and base types once. It follows explicit annotations, confirmed constructors and stable val aliases, resolves explicit this receivers (including known extension receiver types), and classifies named argument labels. Local inheritance lookup preserves ambiguity and does not expand generic substitutions. Branch-local facts cover stable parameters/locals in positive is branches, the corresponding !is else branch, single-condition when branches, short-circuit conditions and explicit casts. Facts do not flow out of branches or into unknown lambda receivers; inferred var initializers are not propagated. Member and annotation lookups are cached within the analysis. Navigation continues to use its separate query planner.
